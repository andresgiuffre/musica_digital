# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Django 5.2 app ("Música Digital") — an ear-training / sight-reading / music-practice platform. Single Django app (`trainer`) holds all models, views, and URLs; there is no DRF/API layer — endpoints are plain Django views returning `JsonResponse`, called from inline `<script>` blocks in the templates. Deployed on PythonAnywhere (see `ALLOWED_HOSTS` in `config/settings.py`).

## Commands

Run all commands from the repo root (where `manage.py` lives).

```bash
python manage.py runserver          # dev server
python manage.py migrate            # apply migrations
python manage.py makemigrations trainer
python manage.py createsuperuser
python manage.py test trainer       # run tests (trainer/tests.py is currently empty)
python manage.py test trainer.tests.SomeTestCase.test_something  # single test
```

Environment variables (all optional except `DJANGO_SECRET_KEY` and `SCORE_FILE_ENCRYPTION_KEY`, neither of which has a dev-safe fallback by design):
- `DJANGO_SECRET_KEY` — required. `config/settings.py` raises `ImproperlyConfigured` at import time if it's missing — fails loud, no fallback (changed from an earlier hardcoded-insecure-key default during a security pass; never add one back).
- `DJANGO_DEBUG` — `'True'`/`'False'` string, defaults to `False`.
- `ANTHROPIC_TEST_API_KEY` — required for the AI orchestration-analysis feature (`orquestador_analizar`) to actually call Claude. Note the name: it's *not* the SDK-conventional `ANTHROPIC_API_KEY`. Without it, the view returns `{"error": "Falta la variable de entorno ANTHROPIC_TEST_API_KEY.", "raw_music_data": ...}` instead of an AI critique — this one degrades softly rather than crashing.
- `SCORE_FILE_ENCRYPTION_KEY` — a Fernet key (see the generation instructions in `config/settings.py`) used to encrypt/decrypt uploaded score files at rest. Deliberately has no default — `trainer/storage.py` raises loudly instead of silently falling back to plaintext if it's missing. Losing this key permanently locks out every previously-uploaded score file; it must never live in the repo or in git.

When `DEBUG` is falsy, `config/settings.py` also turns on `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, `SECURE_SSL_REDIRECT`, and `SECURE_PROXY_SSL_HEADER` (the last one is required on PythonAnywhere specifically — it terminates TLS at its own proxy and talks plain HTTP internally, so without telling Django to trust `X-Forwarded-Proto`, `SECURE_SSL_REDIRECT` loops forever). Don't test locally with `DEBUG=False` unless `HTTPS`/the forwarded-proto header is actually set up, or every request 301s.

One-off data seed scripts at the repo root (`seed_pieces.py`, `seed_gamification.py`, `seed_dictado.py`, `seed_solfeo.py`, `seed_recommended.py`, `fix_req.py`) are run directly with `python <script>.py`, not via `manage.py` — each calls `django.setup()` itself. They populate `Game`, `Achievement`, `Piece`, `DailyGoal` fixture data. Read one before running to know what it seeds/overwrites.

## Architecture

### Data model shape (`trainer/models.py`)

Everything lives in one app, roughly four families of models:

1. **Ear-training games** — `Game` (config: slug, recommended accuracy/attempts to mark "completed"), `Score` (per-user-per-game XP/streak/accuracy, `unique_together('user','game')`), `Attempt` (individual answer log used for per-question-type stats).
2. **Gamification** — `UserProfile` (one per user: total XP, level, daily streak, personal records), `Achievement`/`UserAchievement` (unlocked via slug lookups in `check_achievements()` in `views.py`).
3. **Sheet music / practice tracking** — `Piece` (MusicXML text blob for the games), `SheetMusic`/`Collection`/`Favorite` (the "biblioteca"), `StudySession`, `SheetMusicProgress`, `Playlist`/`PlaylistSheet`, `RehearsalConfig`/`RehearsalLog` (BPM ramp practice), `SheetMarker`/`SheetNote`, `MusicalProject`/`ProjectGoal`/`ProjectSection` (longer-term repertoire tracking with per-section mastery status).
4. **MIDI trainer** — `MidiChordStat` (per-user per-chord mastery, auto-flagged `is_mastered`/`is_problematic` from rolling accuracy), `MidiGameSession`.
5. **Orchestration AI feature** — `ScoreAnalysis` (user, name, the uploaded `.mid`/`.midi`/`.musicxml`/`.mxl` in an encrypted `score_file`, a `JSONField` `analysis_data` with the structured critique, an optional self-referencing `version_de` for re-analyzed revisions, an optional `share_token` for public read-only links). `UserProfile.creditos_analisis`/`creditos_bonus` (two independent, admin-assigned credit pools; see below) gate access. See the dedicated subsection below for how the pipeline actually works.

There are no `ModelForm`s or DRF serializers — views read `request.POST`/`json.loads(request.body)` directly and validate ad hoc.

### Views (`trainer/views.py`, ~1850 lines, one flat module)

- Every game view follows the same pattern: `get_object_or_404(Game, slug=...)`, `Score.objects.get_or_create(...)`, optionally `get_game_stats(user, game)` for the "hardest questions" breakdown, then render a dedicated template.
- `record_attempt` (POST, one endpoint shared by all games via `game_slug`) is the central scoring path: logs an `Attempt`, updates `Score` (streak/points/level via `Score.level_info`), updates `UserProfile` (daily streak, XP, `get_user_level_for_xp`), calls `check_achievements`, and returns the new stats as JSON for the frontend to render without a page reload.
- XP/leveling logic is duplicated in two places that must stay in sync conceptually but are independent: `get_user_level_for_xp()` (global user level, flat XP thresholds in `views.py`) and `Score.level_info` (per-game level, different threshold table in `models.py`).
- `orquestador_analizar` and its supporting views are the odd one out — a whole AI-assisted subsystem built on `music21` + the Anthropic API rather than the game-scoring pattern above. See the dedicated **Orchestration AI feature** subsection below.
- Most mutating endpoints are `@login_required` and accept JSON bodies (not Django forms) — POST-only, manual `try/except` returning `{'status': 'error', 'message': str(e)}`. They are **not** `@csrf_exempt` (that was removed from 14 views in a CSRF-hardening pass) — frontend `fetch()` calls send the token via an `X-CSRFToken` header read from `{{ csrf_token }}`. Exactly two views keep `@csrf_exempt`, each with an inline comment explaining why: `log_study_session` and `api_update_project_state`, both invoked via `navigator.sendBeacon()` (fired on page unload, can't set custom headers, so can't carry a CSRF token) — both also filter by `user=request.user`, so the worst case of the exemption is a user polluting their own data, never another user's.
- Almost every view does local `from .models import X` inside the function body rather than at module scope (existing convention — follow it for new views touching models already imported elsewhere, to avoid circular churn at the top).

### URLs (`trainer/urls.py`)

Flat, no routers/viewsets. Game URLs follow `juego/<slug>/`; most API endpoints are `api/<action>/` or `api/<action>/<id>/`. The orchestration feature's page views live under `orquestador/<action>/` (e.g. `orquestador/historial/`) and its JSON/mutating endpoints under `api/orquestador/<action>/<id>/`. `trainer.urls` is included at the site root in `config/urls.py`, alongside `django.contrib.auth.urls` for login/logout/password views (see `templates/registration/`).

### Frontend

No JS bundler/build step. Per-page logic lives inline in `<script>` blocks inside each `templates/trainer/*.html` file (some are 900+ lines, mixing markup + game logic). Shared pieces:
- `templates/base.html` — the global chrome (navbar, footer, floating theme-toggle button), the "Aprendizaje/Evaluación" mode toggle (persisted in `localStorage['app_mode']`, read via `window.getAppMode()`), and the shared theory-explanation modal (`window.showTheoryModal(title, html, callback)`). Its inline `<style>` block holds **two coexisting CSS token systems** — see **Visual redesign: "Gabinete de estudio"** below before touching colors/tokens on any page.
- `static/js/teoria.js`, `audio_engine.js`, `pitch_tracker_blueprint.js` — the only shared JS modules (music theory helpers, Tone.js-based audio playback, pitch detection).
- Libraries are loaded via CDN `<script>` tags in `base.html` (Tailwind CDN, Tone.js, Tonal.js); VexFlow is loaded per-template where needed for notation rendering.
- Game pages call the shared `/api/record_attempt/<game_slug>/` endpoint via `fetch` and update their own DOM/state from the JSON response — there's no shared frontend state management.

### Static/media

`STATICFILES_DIRS`/`STATIC_ROOT` and `MEDIA_ROOT` are configured normally; `static/audio/piano/` holds piano note samples served to the browser for the audio engine. `MEDIA_URL`/media serving is only wired up when `DEBUG=True` (see `config/urls.py`) — direct `/media/` URLs are **not** authenticated in production (PythonAnywhere serves that path itself via a static-files mapping, bypassing Django/`@login_required` entirely). `ScoreAnalysis.score_file` doesn't care (it's Fernet-encrypted at rest — see below). `SheetMusic.xml_file` used to be linked directly (`sheet.xml_file.url`), which leaked scores to anyone with the URL; it's now served through `biblioteca_archivo` (`@login_required`, streams via `FileResponse`), and templates must use `{% url 'biblioteca_archivo' sheet.id %}`, never `sheet.xml_file.url`, for anything user-facing.

### Visual redesign in progress: "Gabinete de estudio" (`static/css/gabinete.css`)

The site is mid-migration from an older dark-by-default design ("Sala de conciertos" — the `:root` token block still in `base.html`'s `<style>`: `--gold`/`--wine`/`--petroleo`/`--parchment*`/`--surface`/`--border`/`--text`/`--text-secondary`/`--bg`/`--success`/`--warning`/`--danger`/`--paper`, toggled light via `data-tema="claro"` on `<html>`, dark by default) to a new light-by-default design, "Gabinete de estudio" (Newsreader serif + Archivo sans, ciruela `#6b3550` as the *only* action color, slate/ochre/green/brown/rose reserved strictly for category accents — never buttons). **Both systems are live in the codebase at once**; which one a given template renders is purely a function of whether it has opted in — nothing is deleted or shared by default.

**How a page opts in** — three template blocks, always together:
1. `{% block html_attrs %}data-gabinete-page{% endblock %}` — stamps the attribute on `<html>` before `<body>` exists, so the anti-flash theme script in `base.html`'s `<head>` can tell which of the two *independent* theme systems to read (see below).
2. `{% block body_class %}gabinete{% endblock %}` — the actual switch. Every Gabinete token for page *content* is scoped `body.gabinete { ... }` in `gabinete.css`; without this class the page still gets the new global navbar/footer (see next point) but none of the new content styling.
3. `{% block nav_active_<name> %}is-active{% endblock %}` — one of five blocks base.html defines empty by default (`panel`/`biblioteca`/`entrenamiento`/`analizador`/`orquestar`), underlines the matching navbar link.

**Why the two systems can't share token names**: `body.gabinete` redefines several names the old system already claims at `:root` with a *different* meaning — `--bg`, `--surface`, `--ink`, `--primary`, `--danger`, `--font-display`, `--font-body`. Higher specificity means `body.gabinete`'s values always win inside a migrated page (intended), but it also means: **never** add a new `body.gabinete`-scoped override using one of these exact names without checking what it breaks, and **any** old shared component class reused on a migrated page needs a matching override in `gabinete.css` or it silently inherits half-old/half-new values. This already happened and was fixed for `.card`, `.btn-submit`, `.btn`, `.btn-input`, `.form-group`, `.progress-container`/`.progress-labels`/`.progress-track`/`.progress-fill`, `.status-bar`, `.flash-correct`/`.flash-incorrect` (all originally defined once in `base.html` for the old game-UI, all now also overridden under `body.gabinete` in `gabinete.css` so the ~10 `trainer_*.html` game templates didn't need their markup touched at all).

**Chrome (navbar + footer + floating theme-toggle button) is global and unconditional** — `.navbar-gab`/`.footer-gab`/`.tema-toggle-btn--gab` in `gabinete.css` carry their *own* self-contained copy of the light/dark token set (not gated behind `body.gabinete`), because the navbar was replaced site-wide in one pass before all page content had migrated. A not-yet-migrated page (old dark theme) still renders under the new light navbar — a known, accepted visual seam during the transition, not a bug to fix per-page.

**Two independent theme toggles share one floating button**: the old system's dark/light state lives in `data-tema` on `<html>` (default dark, `"claro"` = light, `localStorage['color_scheme']`). The new system uses a *different* attribute, `data-tema-gabinete` (default light, `"oscuro"` = dark, `localStorage['color_scheme_gabinete']`) — kept separate on purpose so switching one page's theme never touches the other system's remembered preference. `base.html`'s toggle-button JS branches on `document.documentElement.hasAttribute('data-gabinete-page')` to pick which attribute/key to touch. The Gabinete dark variant isn't from any design spec — the design brief only defines a light theme — it was derived from the one dark-mode hint available (`--rose` is documented there as "acento sobre fondo oscuro").

**Sheet music paper is theme-invariant in both systems**: `--score-paper`/`--score-ink` (Gabinete) and `--paper` (old) are never redefined by either dark variant — notation always renders on white with near-black ink regardless of site or page theme.

**Migrated**: `dashboard.html`, `biblioteca_list.html`, `biblioteca_play.html`, `entrenador_index.html`, every reachable `trainer_*.html` game screen (notas/intervalos/intervalos_auditivos/dictado_melodico/lectura_musical/tiempos_fuertes/sincopas/acordes/progresiones), `orquestador_analizar.html`/`orquestador_historial.html`/`orquestador_historial_detalle.html`/`orquestador_publico.html`, `orquestacion_ejercicio.html`/`orquestacion_ejercicio_lista.html`, `midi_hub.html`, `midi_game_chords.html`, `proyectos_list.html`, `proyecto_detail.html`, `cursos_list.html`/`curso_detail.html`/`tema_detail.html` (see **Cursos** below — this reverses that feature's original "no Gabinete styling yet" scoping decision; it was migrated once the rest of the site's non-Cursos pages caught up). `orquestador_publico.html` doesn't extend `base.html` at all (no login, no navbar — see below) so it can't use `body.gabinete`; it defines the same Gabinete token names directly in its own `:root` instead, kept in sync by hand.

**Not yet migrated**: `perfil.html`, `playlists_list.html`, everything in `templates/registration/`, `orquestador_pdf.html` (renders through `xhtml2pdf`, a separate constrained rendering path — may not want the same treatment at all). `trainer.html` and `trainer_solfeo_ritmico.html` are both dead code with no URL pointing at them; the latter got migrated along with the rest of `trainer_*.html` for consistency but has never been exercised in a real browser.

**Dashboard pentagram background**: the "Espacios de trabajo" section on `dashboard.html` has a large decorative inline SVG (`.espacios-gab__pauta-fondo` — staff lines + a real treble-clef path from Wikimedia Commons + note glyphs) behind the workspace-card grid, at very low opacity (`var(--primary)`, ~0.08 light / ~0.13-0.15 dark). This is the same SVG markup the pre-Gabinete `dashboard.html` used behind its old "Explorar" section (recovered from git history at commit `1da7aaf1`) — recolored from the old hardcoded `var(--gold)` to `var(--primary)` so it follows the Gabinete theme toggle automatically instead of needing a separate light-theme override like the old version had.

**Reusable Gabinete components** (`gabinete.css`) worth knowing before adding a new migrated page: `.volver-gab` (the standard small "back one step" link — not necessarily back to the dashboard, back to whatever's structurally above the current page — replaces the old per-page "Volver" button markup); `.btn-gab`/`.btn-gab--primary`/`--secondary`/`--on-dark` (buttons — elevate `-2px` + `--shadow-hover` on hover); `.card-gab`/`.card-gab--hoverable` (generic hoverable card — elevates `-6px` + the stronger `--shadow-lift` on hover). Several screen-specific card classes (`.espacio-gab`, `.partitura-gab`, `.fragmento-gab`, `.etapa-gab__card`) duplicate that same `-6px`/`--shadow-lift` hover treatment locally instead of using `.card-gab` directly — match it if adding another.

**One color literal that can't live in CSS**: `ZONAS_EJERCICIO_ORQUESTACION` in `views.py` (a module-level constant, same pattern as `COLOR_NOTA_EDITADA` elsewhere in the file) hardcodes the 5 instrument-painting colors for the orchestration color exercise as Python hex literals, kept in sync by hand with `gabinete.css`'s palette — Python can't read CSS custom properties.

### Cursos feature (`Curso`/`Grado`/`Tema`/`BloqueContenido`)

A separate, simpler educational-content feature: theory content organized `Curso` → `Grado` (numbered, e.g. "Grado 0") → `Tema` (slug within its grado) → `BloqueContenido` (ordered content blocks within a tema). Views: `cursos_list`/`curso_detail`/`tema_detail` in `views.py`, right after `orquestacion_ejercicio_archivo`. URLs mix `id`-based `Curso` lookup with human-readable `grado_numero`/`tema_slug` (`cursos/<int:curso_id>/grado/<int:grado_numero>/<slug:tema_slug>/`) — a deliberate, narrow exception to the site's otherwise all-`id` URL convention, scoped to just this one model chain.

- **`BloqueContenido.tipo`** is one of `TEXTO`/`EJEMPLO_PARTITURA`/`PRACTICA`, each with its own nullable fields validated in `clean()` (e.g. `EJEMPLO_PARTITURA` requires exactly one of `sheet_music`/`fragmento_orquestacion`, never both/neither). `EJEMPLO_PARTITURA` reuses the existing `biblioteca_archivo`/`orquestacion_ejercicio_archivo` file-serving views rather than adding a new one; `tema_detail` precomputes `bloque.es_mxl` server-side (same pattern as the orchestration exercise) so the frontend OSMD loader never has to guess the file extension.
- **Markdown rendering is this project's first-ever `mark_safe()` call**: `trainer/services.py`'s `render_markdown_seguro()` runs `TEXTO` blocks' `texto_markdown` through `markdown.markdown()` then `nh3.clean()` (explicit tag/attribute allow-list — confirmed empirically, not assumed, to strip both `<script>` and `javascript:`-scheme link hrefs) before wrapping the sanitized output in `mark_safe()`. This is the only place in the codebase that does this — never add `|safe`/`mark_safe`/`format_html` elsewhere in the Cursos flow without the same sanitize-then-mark-safe discipline.
- **Cascading `activo` flags**: `cursos_list`/`curso_detail`/`tema_detail` each `get_object_or_404` with `activo=True` at every level of the chain (curso → grado → tema) — deactivating any ancestor 404s everything below it.
- **Admin**: `CursoAdmin`/`GradoAdmin` use `TabularInline` for their children; `TemaAdmin` uses a `StackedInline` for `BloqueContenido` (its ~7 type-specific fields don't fit a table) with fieldsets grouped by `tipo`, plus a `ver_renderizado` link (`reverse('tema_detail', ...)`) to preview the live page. No drag-and-drop ordering — `orden`/`numero` are plain integer fields, renumbered by hand.
- **Visual design**: originally built without Gabinete styling on purpose (explicit user instruction — visual design was deferred to a later mockup pass), then migrated to Gabinete once the rest of the site's remaining non-Cursos pages (`midi_hub.html`, `proyectos_list.html`, etc.) caught up — see **Migrated** in the Gabinete section above. No navbar entry exists for Cursos; it's reached via the "Cursos" promo card on `dashboard.html` (the `.placa-gab` panel next to "Director de Estudio", both styled as premium dark panels) — adding a top-nav link remains unscoped, same as it was when Cursos first shipped.

### Orchestration AI feature (`orquestador_*`)

An AI-assisted orchestration critique tool: a user uploads a score, `music21` extracts structured data deterministically, Claude (Anthropic API) writes a prose critique constrained to a forced tool schema, and the result is stored, browsable, exportable to PDF, and optionally shareable via a public link. Spans `trainer/views.py` (all `orquestador_*` views plus the deterministic helpers below `ORQUESTACION_TOOL`), `trainer/prompts.py` (the system prompt), `trainer/storage.py` (file encryption), `trainer/services.py` (`consumir_credito_analisis`), and `templates/trainer/orquestador_*.html`. `trainer/orquestador_gemini_legacy.py` is a dead reference file from an earlier Gemini-based prototype — not imported anywhere, kept only for history; `google-genai` is not in `requirements.txt`.

- **Credits gate access, not a paywall check per se**: `UserProfile` has two independent integer pools, `creditos_analisis` (admin-assigned "monthly" allotment) and `creditos_bonus` (never expires). `orquestador_analizar` rejects the request with HTTP 403 if both are `<= 0`. On genuine success, `services.consumir_credito_analisis()` decrements `creditos_analisis` first and only falls through to `creditos_bonus` if that's already 0 — both decrements are conditional `UPDATE ... WHERE creditos_X__gt=0` calls (via `F()`), not read-modify-write in Python, specifically to stay race-safe under concurrent analyses for the same user.
- **Files are encrypted at rest**: `ScoreAnalysis.score_file` uses `trainer.storage.EncryptedFileSystemStorage`, which wraps Django's `FileSystemStorage` to Fernet-encrypt on `_save()` and decrypt on `_open()` (key from the `SCORE_FILE_ENCRYPTION_KEY` env var — see Environment variables above). Callers don't need to know this — `FileField.open()`/`.read()` behave normally. `_parsear_score_descifrado()` (`views.py`) reads the decrypted bytes and parses with `music21` fully in memory (handling `.mxl` zip extraction, `.mid`/`.midi`, and raw `.musicxml`/`.mxl`-unwrapped XML) — the decrypted content is never written to disk, even transiently.
- **Deterministic pre-analysis (no AI) feeds the prompt**: for each part, `calcular_estadisticas_parte` (range, note count, rests, most-frequent pitch class), `evaluar_viabilidad_instrumental` (comfortable-register warnings), and `calcular_densidad_por_compas` (active-instrument count per measure, for the density heatmap) all run before Claude is ever called. `detectar_duplicaciones_verificadas(parts)` is the key one: it walks every pair of parts measure-by-measure and classifies the relationship between their sounding pitches (`_eventos_sonantes_por_compas` extracts one pitch per note-attack per measure, ignoring rests and unpitched percussion; `_clasificar_relacion` compares two same-measure attack sequences) as `unísono`, `octava`, `intervalo_fijo`, or `sin_relacion` — **a mismatched attack count between the two parts is always `sin_relacion`**, doubling requires matching rhythm, not just matching pitches at some point. Contiguous same-classification measures are merged into ranges. This replaced having Claude eyeball doubling from raw pitch data, which it did unreliably.
- **The Claude call**: `client.messages.stream(...)` (model `claude-sonnet-5`, `max_tokens=48000`, forced `tool_choice` on `ORQUESTACION_TOOL`, system prompt = `GUIA_ESTILO_ORQUESTAL` from `trainer/prompts.py` with `cache_control: ephemeral`). The prompt is the JSON-dumped deterministic `analysis_data` (including `duplicaciones_verificadas`, which is sent to Claude but **never merged into the data returned to the frontend** — it's internal-only, feeding the prompt, not the API response). `GUIA_ESTILO_ORQUESTAL` is the single source of truth for output style: it forbids asserting a doubling/unison/octave relationship except when backed by an exact-range entry in `duplicaciones_verificadas`, forbids duplicating content between schema fields (`resumen_general` vs `bloques` vs `resumen_por_instrumento`), and defines the mechanical-edit vocabulary (`transponer_octava`/`silenciar`/free-text with `accion_tipo: null`).
- **Auditing "verificado" claims against the data**: `GUIA_ESTILO_ORQUESTAL` alone can't *guarantee* Claude never writes "verificado"/"verificada" without real backing, so the schema also requires each block to carry `duplicaciones_citadas` (array, may be empty) — the exact `duplicaciones_verificadas` entries backing any such claim in that block's prose. `_auditar_citas_duplicaciones()` (`views.py`) cross-checks this after every analysis, log-only (never blocks or edits the output — the point right now is to collect real cases before deciding whether rejecting/retrying is worth it): it flags either an empty `duplicaciones_citadas` alongside "verificado" language that isn't negated, or a cited entry that doesn't match any real `duplicaciones_verificadas` entry (same unordered part pair, same `tipo`, overlapping measure range). "Isn't negated" is decided by `_hay_negacion_cercana()`, a heuristic that scans the whole clause containing the match (bounded by the nearest `.`/`,`/`;`, since Spanish negation scope is clause-wide rather than a fixed word count) for "sin"/"no" — added specifically to stop flagging legitimately cautious phrasing like "sin que exista una entrada de duplicación verificada".
- **Streaming, not request/response**: the view returns a `StreamingHttpResponse` yielding NDJSON lines — `{"heartbeat": true}` on every stream event (including during the `music21` parsing loop, one per part) plus a final `{"status": "success"/"error", ...}` line. This exists specifically because PythonAnywhere's proxy silently drops long (~100s+) idle connections even though the backend eventually returns 200 — heartbeats keep real bytes flowing the whole time. The stream's raw `partial_json` text is accumulated manually and parsed with strict `json.loads()` rather than trusting the SDK's tolerant final snapshot, and `_limpiar_fuga_json_en_resumen()` defensively truncates `resumen_general` if it ever contains an escaped, validly-parseable copy of another schema field (a real, occasionally-observed Claude generation artifact under this schema's size) — worst case a user sees a slightly shorter summary, never raw leaked JSON. Frontend counterpart: `leerRespuestaEnStream()` in `orquestador_render.js`, which reads the body stream, skips heartbeat lines, and treats the last line as the result.
- **Versioning**: uploading a new file with `version_de_id` set links it to a prior `ScoreAnalysis`. `comparar_versiones()` deterministically re-checks each mechanically-executable suggestion (`accion_tipo` of `transponer_octava`/`silenciar`) from the prior analysis against the new file's actual notes in that measure range (silence check, or average-register shift past a 6-semitone threshold) and marks it `resuelto`/`no_resuelto`; free-text suggestions (`accion_tipo: null`) always come back `sin_verificar` — they can't be checked mechanically.
- **Other endpoints**: `orquestador_historial`/`orquestador_historial_detalle` list/view past analyses. `orquestador_fragmento_edicion` (GET, `accion_tipo=transponer_octava` only) re-parses the original file and returns before/after MusicXML fragments (`generar_fragmento_comparado`, ±`CONTEXTO_COMPASES` measures of unchanged context, edited notes colored red) for OSMD side-by-side rendering in the browser. `orquestador_exportar_pdf` renders `orquestador_pdf.html` through `xhtml2pdf`/`pisa`; because the PDF can't run the frontend JS that draws the register map and density heatmap, `_calcular_mapa_registros`/`_preparar_densidad_pdf` recompute those same visuals as plain Python/CSS. `orquestador_generar_link`/`orquestador_revocar_link` issue/clear a random `share_token` (`secrets.token_urlsafe(32)`); `orquestador_publico` is the only view in this whole feature without `@login_required` — anyone with the token URL gets a read-only page.
